Измерения оптимизации Purge Memory Preview, 10 ноября 2026 года.

Apple M1, 8 ГБ RAM, macOS 27.2.1, Xcode 27.2. Обе версии собраны в Release (`-O`, wholemodule), arm64, без покрытия кода. Сравниваются коммит `449b3f0fa300a667b271ce6202e9e84273b65a49` и текущие изменения оптимизации. Измерительные копии и журналы сохранены в `/private/tmp/purge-optimization-benchmark`.

Основной выигрыш подтверждён при обработке большого списка результатов: время уменьшилось примерно в 3,43 раза, процессорное время — на 63,5%. Большого выигрыша при обработке групп процессов не получено. Устойчивое снижение RAM и CPU в простое этими измерениями не установлено.

Для быстрых сценариев ниже приведены медианы пяти повторов после прогрева. CPU — суммарное процессорное время самого процесса, user + system, а не загрузка всего Mac.

| Сценарий | До | После | Изменение |
| --- | ---: | ---: | ---: |
| Large Files: 1 000 строк, время | 28.56 мс | 23.13 мс | −19.0% |
| Large Files: 1 000 строк, CPU | 35.90 мс | 30.79 мс | −14.3% |
| Large Files: 10 000 строк, время | 738.22 мс | 215.26 мс | −70.8% |
| Large Files: 10 000 строк, CPU | 825.11 мс | 301.52 мс | −63.5% |
| 1 000 снимков групп процессов, время | 991.90 мс | 957.88 мс | −3.4% |
| Отмена команды sleep 2, задержка | 1950.83 мс | 509.93 мс | −73.9% |

Публикации Large Files: для 1 000 строк **43 → 3**, для 10 000 строк **403 → 4**. Счёт включает очистку списка и финальную публикацию. Проверки количества строк и порядка сортировки прошли. Контрольная сумма обработки групп процессов совпала: `16005320000`.

Здесь измеряется настоящий `PurgeStore.scanLargeFiles` с одинаковыми метаданными из `FakeScans`. Обход файловой системы, рендеринг SwiftUI и хеширование дубликатов в этот сценарий не входят. Поэтому ускорение в 3,43 раза относится к обработке результатов, а не ко всему сканированию диска. Для групп процессов один повтор включает создание, сортировку и повторные чтения 1 000 снимков по 200 групп с восемью участниками.

Наблюдение за памятью: один запуск на сценарий, создание координатора плюс 30 секунд. Для управляемого сценария в обеих временных копиях одинаково разрешён запуск наблюдателей внутри тестового хоста, активность приложения принудительно выставлена в true, а скрытое тестовое окно сообщает о своей видимости. Остальные проверки TestHost сохранены. Реальный провайдер процессов используется; очистка не вызывается. Эти цифры не являются устойчивой оценкой CPU или расхода батареи.

| Сценарий за 30 секунд | До | После |
| --- | ---: | ---: |
| Простой: CPU | 239.9 мс (0.80%) | 249.3 мс (0.83%) |
| Свёрнутый список: CPU | 464.7 мс (1.55%) | 145.9 мс (0.49%) |
| Свёрнутый список: опросы процессов | 6 | 0 |
| Тики выключенной автоочистки, в каждом сценарии | 3 | 0 |

В процентах одно ядро принимается за 100%. Уменьшение лишних опросов и тиков подтверждено счётчиками; малые различия CPU в простое нельзя приписать оптимизации.

RAM измерялась через TASK_VM_INFO у процесса тестового хоста приложения. Это значения на концах сценария, не пиковое потребление и не количество освобождённой системной RAM.

Но история выделений, переиспользование страниц аллокатором, фоновые службы и освобождение страниц во время 30-секундного ожидания влияют на значения. Отмена измерялась отдельно на настоящем ProcessRunner, скомпилированном с `swiftc -O`. Дочерняя команда sleep работает две секунды, отмена запрашивается через 50 мс после маркера готовности. Старая версия дожидается естественного завершения, новая посылает SIGTERM и завершает ожидание. Это не замер обхода du и не проверка ожидания полного тайм-аута 300 секунд.
